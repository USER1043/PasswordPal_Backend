# Contributing to PasswordPal Backend

Thanks for helping out. This guide covers setting up, the conventions we follow, and what a good pull request looks like. For how the system fits together, read [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) first.

This service handles authentication and encrypted user data. Please read [SECURITY.md](SECURITY.md) before touching anything in `controllers/authController.js`, `controllers/totpController.js`, `middleware/` or `utils/`.

## Setup

```bash
git clone https://github.com/USER1043/PasswordPal_Backend.git
cd PasswordPal_Backend
npm install
cp .env.example .env
npm test
```

`npm test` needs no database and no real secrets, because tests mock Supabase. You only need a Supabase project and a filled-in `.env` to run the server itself (`npm run dev`). See the [README](README.md) for the full setup.

## Workflow

1. Fork or branch from `main`. Use a descriptive branch name such as `fix/totp-replay` or `feat/device-heartbeat`.
2. Make a focused change. One concern per pull request.
3. Add or update tests (see below).
4. Run `npm test` and make sure it passes.
5. Open a pull request against `main` and describe what changed, why, and how you checked it.

## Commit messages

We use [Conventional Commits](https://www.conventionalcommits.org/): `type(scope): summary`, in the imperative, lower case, no trailing period.

```
fix(totp): refuse a code that was already used
feat(devices): add a session heartbeat endpoint
docs: describe the recovery flow
chore(db): drop unused recovery_keys columns
```

Common types: `feat`, `fix`, `docs`, `test`, `refactor`, `chore`. Explain the reason in the body when it is not obvious.

## Code layout and style

Requests flow `route/` → `validators/` → `controllers/` → `models/`. Keep each layer to its job:

- **Routes** only wire URLs to middleware and controllers.
- **Validators** (Joi) reject malformed input before a controller runs. Add a schema for any new body or query.
- **Controllers** decide the response. They do not build SQL.
- **Models** are the only place that talks to Supabase.
- Cross-cutting logic (rate limiting, TOTP, sessions, recovery signature) lives in `utils/`.

Follow the style of the surrounding code: ES modules, `async/await`, short comments that explain why rather than what. Reuse the existing helpers before writing new ones, for example `isRateLimited` / `recordFailedAttempt` in `utils/attemptLimit.js`, `setSessionCookies` / `issueSession` in `utils/session.js` and `verifyTotp` in `utils/totp.js`.

### Rules specific to this project

- **Never log or return secrets**: passwords, `auth_hash`, tokens, TOTP secrets, backup codes, challenges.
- **Failed secret checks count against the shared limiter.** If you add an endpoint that checks a password, code or key, call `isRateLimited` first and `recordFailedAttempt` on failure. If you add a new failure reason, extend the `login_attempts.failure_reason` CHECK constraint in a migration.
- **Return the same response for "unknown user" and "wrong secret"** wherever the endpoint can be used to probe accounts.
- **Protect sensitive actions** with `verifySession`, and with `requireFreshAuth` when they should need a recent password check.
- The server must stay unable to decrypt vaults. Do not add code that would receive a master password or an unwrapped vault key.

## Tests

Tests live in `tests/` and run with Vitest and Supertest. They mock `config/db.js` (the Supabase client) and the model modules, so a test describes the behaviour of one controller or helper without a database. Look at `tests/totpReplay.test.js`, `tests/recovery.test.js` and `tests/attemptLimit.test.js` for patterns.

- Test the behaviour you changed, including the failure paths (wrong code, rate limited, expired).
- When a controller gains a new model import, update the mocks in existing tests that load it.
- Cryptographic changes need a known-answer test. `tests/recoverySignature.test.js` verifies a signature generated by the Rust app against the server's verifier.

## Database changes

1. Add a migration at `scripts/migrations/YYYY-MM-DD_short_description.sql`. Write it so it can run twice (`IF NOT EXISTS`, `IF EXISTS`).
2. Mirror the change in `scripts/init_db.sql` so a fresh project gets the same schema.
3. Update `validators/schemas.js` if a table's shape changed.
4. Keep Row Level Security on and the `anon`/`authenticated` roles closed. `tests/dbAccess.test.js` checks this.
5. Note in the pull request that the migration must be run in Supabase after the code is deployed (or before, if the code needs it first).

## Pull request checklist

- [ ] The change is focused and the description says why it is needed
- [ ] `npm test` passes
- [ ] New behaviour and failure paths are tested
- [ ] No secrets, tokens or personal data in code, tests or logs
- [ ] A migration and `scripts/init_db.sql` update are included if the schema changed
- [ ] `docs/` and the README are updated if behaviour, endpoints or configuration changed

## Reporting bugs and vulnerabilities

Open an issue for bugs and feature ideas. Report security problems privately, as described in [SECURITY.md](SECURITY.md).
